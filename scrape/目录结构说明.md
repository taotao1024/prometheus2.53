# Prometheus scrape 目录结构说明

> 基于 Prometheus v2.53 源码整理。
> `scrape/` 是 Prometheus 的**抓取（scrape）引擎**：接收服务发现推送的目标组，为每个目标维护
> 一个定时抓取循环，通过 HTTP 拉取指标、解析文本/OpenMetrics/Protobuf 格式、做 relabel，
> 再通过 `storage.Appender` 写入存储。
> 它随 `prometheus` 二进制运行（**Server 与 Agent 模式都会启用**），不是独立服务、无监听端口
> （它对目标而言只是 HTTP **客户端**）。

## 一、整体架构（抓取流程）

```
 ① 目标来源
    discovery.Manager.SyncCh()  map[string][]*targetgroup.Group
        │  （kubernetes_sd / file_sd / static_configs …）
        ▼
 ② 抓取池管理：scrape.Manager（manager.go）
    Run(tsets) → reloader 协程 → sync(tsets) → 为每个 job 维护一个 scrapePool
    ApplyConfig() 配置重载：新增/修改/删除 job 的 pool
        ▼
 ③ 目标与循环：scrapePool + scrapeLoop（scrape.go）
    每个 target 一个 scrapeLoop goroutine：
      run()：按 scrape_interval（含 hash 偏移错峰）定时触发
        └─ scrapeAndReport()
             ├─ scrape()：HTTP GET {scheme}://{addr}{metrics_path}?{params}
             │    · 认证（basic/bearer/OAuth2/TLS）、超时 = scrape_timeout
             │    · 解析：Prometheus text / OpenMetrics / Protobuf（clientprotobuf.go）
             │    · 限制：body_size_limit、sample_limit、label_limit、native histogram bucket limit
             ├─ metric_relabel_configs：丢弃/改写样本
             ├─ Appender：写入 fanoutStorage（TSDB / Agent WAL）
             └─ report()：生成 up、scrape_duration_seconds、scrape_samples_scraped… 等合成样本
        ▼
 ④ 观测
    GET /api/v1/targets（active/dropped）、/targets/metadata、Web UI /targets
    prometheus_target_* 指标 + 每个目标的 up / scrape_* 序列
```

## 二、目录结构总览

```
scrape/
├── manager.go          # ★ 抓取管理器：接收 SD 目标组、维护 scrapePool、配置热重载、targets 查询
├── scrape.go           # ★ 抓取循环：scrapePool、scrapeLoop、HTTP 抓取、解析、relabel、写库、上报
├── target.go           # ★ 目标模型：Target、TargetHealth、URL/标签/元数据/间隔与偏移计算
├── metrics.go          # 抓取层的全局指标注册与自定义 Collector（含 metadata 缓存指标）
├── clientprotobuf.go   # Protobuf 暴露格式的编码辅助（主要供测试构造 protobuf 抓取输入）
├── manager_test.go     # 管理器测试：pool 增删、热重载、target 统计、失败日志
├── scrape_test.go      # 抓取循环测试：解析、限制、relabel、timestamp、staleness
├── target_test.go      # 目标测试：标签、URL、offset、外部标签、元数据
├── helpers_test.go     # 测试辅助（构造配置、启动 mock HTTP 服务等）
└── testdata/           # 测试用证书与 token
    ├── ca.cer / ca.key
    ├── client.cer / client.key
    ├── server.cer / server.key
    ├── servername.cer / servername.key
    └── bearertoken.txt
```

## 三、文件功能说明

| 文件 | 功能 |
|------|------|
| `manager.go` | **抓取管理器**。<br>• `Options`：`ExtraMetrics`（额外抓取指标）、`NoDefaultPort`、`HTTPClientOptions`、`ScrapeFailureLogFile`、`DiscoveryReloadInterval`、`SkipOffsetting` 等<br>• `NewManager(opts, logger, app storage.Appendable, registerer)`：创建管理器<br>• `Run(tsets <-chan map[string][]*targetgroup.Group)`：接收 SD 目标组，交给后台 `reloader` 同步（不阻塞 SD）<br>• `ApplyConfig(cfg)`：配置热重载，对比 `scrape_configs` 增删改 `scrapePool`<br>• `TargetsActive()` / `TargetsDropped()` / `TargetsAll()` / `TargetsDroppedCounts()` / `ScrapePools()`：供 `/api/v1/targets` 展示<br>• `Stop()` / `UnregisterMetrics()`：优雅停止并反注册指标<br>• `PopulateLabels()` / `TargetsFromGroup()`：把发现的目标组转成 `Target`（也被 `promtool check service-discovery` 复用） |
| `scrape.go` | **抓取循环实现（本包最核心、最长的文件）**。<br>• `scrapePool`：一个 job 的目标集合，负责 `sync`（增删 target）、`reload`（配置变更后重建 loop）<br>• `scrapeLoop` + `newScrapeLoop()` + `run()`：每个目标一个 goroutine，按 `interval` 定时抓取（`offset()` 按目标 hash 错峰）<br>• `scrapeAndReport()`：一次抓取的完整流程（HTTP 请求 → 解析 → relabel → append → 上报）<br>• 解析器与缓存：`scrapeCache`（指标名/标签驻留、去重）、`sampleMutator`、`labelsMutator`<br>• 限制与保护：`labelLimits`（`label_limit`/`label_name_length_limit`/`label_value_length_limit`）、body/sample 上限、超时<br>• `report()` / `reportStale()`：生成 `up`、`scrape_duration_seconds`、`scrape_samples_scraped`、`scrape_samples_post_metric_relabeling`、`scrape_series_added`、`scrape_timeout_seconds`、`scrape_sample_limit`、`scrape_body_size_bytes` 等合成样本；目标消失时写 staleness 标记<br>• `ScrapeTimestampTolerance` / `AlignScrapeTimestamps`：抓取时间戳对齐与容差<br>• `scrapeFailureLogFile` 支持：抓取失败时把样本落盘便于排查 |
| `target.go` | **目标模型**。<br>• `TargetHealth`：`up` / `down` / `unknown`<br>• `Target`：`labels`（最终标签）、`discoveredLabels`（relabel 前）、`params`、`interval`/`timeout` 等<br>• `NewTarget()`、`Labels()`、`DiscoveredLabels()`、`URL()`、`String()`<br>• `hash()` / `offset()`：按目标标签 hash 计算抓取偏移，把同 job 的目标**均匀铺开**到 interval 内，避免同秒齐发<br>• `Report()` / `LastError()` / `LastScrape()` / `LastScrapeDuration()` / `Health()`：抓取结果上报与查询<br>• `MetricMetadataStore` / `MetricMetadata` / `ListMetadata()` 等：目标级指标元数据缓存（供 `/api/v1/targets/metadata`）<br>• `intervalAndTimeout()`：解析目标上的 `__scrape_interval__`/`__scrape_timeout__` 标签覆盖<br>• `GetValue()`：读取 `__param_*` 等特殊标签 |
| `metrics.go` | **抓取层全局指标**：`scrapeMetrics` 结构集中定义并注册 `prometheus_target_*` 指标（见下表）；`TargetsGatherer` 接口供自定义 Collector 查询目标数；`MetadataMetricsCollector` 为 metadata 缓存提供自定义 Collector；`Unregister()` 便于测试与优雅关闭 |
| `clientprotobuf.go` | Protobuf 暴露格式（`prometheus.WriteRequest` / `MetricFamily`）的编码辅助函数，**主要用于测试**构造 protobuf 格式的抓取响应，配合 `--enable-feature=native-histograms` 等场景验证解析路径 |
| `manager_test.go` | 测试：pool 创建/删除、`ApplyConfig` 增量更新、target 计数与 dropped 限制、失败日志文件 |
| `scrape_test.go` | 测试：各格式解析、relabel、sample/label/body 限制、时间戳对齐与容差、staleness、抓取超时、exemplar 与 native histogram |
| `target_test.go` | 测试：`NewTarget`、URL 构造（默认端口/scheme）、offset 计算、external labels、元数据存取 |
| `helpers_test.go` | 测试辅助函数：构造 `ScrapeConfig`、生成 mock 指标响应、启动 `httptest` 服务 |
| `testdata/` | 测试用 TLS 证书（CA/client/server/servername 的 cer+key）与 `bearertoken.txt`，用于验证 HTTPS、mTLS、bearer token 配置 |

## 四、指标一览

### 4.1 全局抓取指标（`metrics.go`）

| 指标 | 含义 |
|------|------|
| `prometheus_target_scrape_pools_total` | 创建的抓取池总数 |
| `prometheus_target_scrape_pools_failed_total` | 抓取池创建失败数 |
| `prometheus_target_scrape_pool_reloads_total` / `..._failed_total` | 抓取池重载次数 / 失败数 |
| `prometheus_target_scrape_pool_targets` | 各 pool 当前目标数 |
| `prometheus_target_scrape_pool_target_limit` | 各 pool 的目标数上限（`--scrape.target-limit` / `target_limit`） |
| `prometheus_target_scrape_pool_exceeded_target_limit_total` | 超出目标数上限次数 |
| `prometheus_target_scrape_pool_sync_total` | 目标同步次数 |
| `prometheus_target_sync_failed_total` | 目标同步失败次数 |
| `prometheus_target_scrapes_exceeded_body_size_limit_total` | 超过 `body_size_limit` 次数 |
| `prometheus_target_scrapes_exceeded_sample_limit_total` | 超过 `sample_limit` 次数 |
| `prometheus_target_scrapes_sample_duplicate_timestamp_total` | 重复时间戳样本数 |
| `prometheus_target_scrapes_sample_out_of_order_total` / `..._out_of_bounds_total` | 乱序/越界样本数 |
| `prometheus_target_scrape_pool_exceeded_label_limits_total` | 超出标签限制次数 |
| `prometheus_target_scrapes_exceeded_native_histogram_bucket_limit_total` | 超出原生直方图桶限制次数 |
| `prometheus_target_scrapes_exemplar_out_of_order_total` | 乱序 exemplar 数 |
| `prometheus_target_scrapes_cache_flush_forced_total` | 抓取缓存被迫刷新的次数 |

### 4.2 每个目标产生的合成序列（`scrape.go` 的 `report()`）

`up`、`scrape_duration_seconds`、`scrape_samples_scraped`、`scrape_samples_post_metric_relabeling`、`scrape_series_added`、`scrape_timeout_seconds`、`scrape_sample_limit`、`scrape_body_size_bytes`（带目标的 `job`/`instance` 等标签）。

## 五、归属

- **归属服务**：Prometheus 的**抓取引擎**，随 `prometheus` 二进制运行：
  - **Server 模式**：抓取 → 写入本地 TSDB + remote write 队列（`fanoutStorage`）；
  - **Agent 模式**：抓取 → 写入 Agent 的 WAL-only 存储，再远程写出去（无规则/无告警）；
  - 不是独立服务、无监听端口；对目标来说是 HTTP 客户端。
- 本包部分函数（`PopulateLabels`、`TargetsFromGroup`）被 **`promtool check service-discovery`** 复用。

## 六、访问入口

### 1. 配置入口（`prometheus.yml`）

```yaml
global:
  scrape_interval: 15s          # 默认抓取间隔
  scrape_timeout: 10s           # 默认抓取超时（不得超过 interval）

scrape_configs:
  - job_name: node
    metrics_path: /metrics      # 默认 /metrics
    scheme: http                # http | https
    scrape_interval: 10s        # 覆盖 global
    scrape_timeout: 5s
    honor_labels: false         # 是否保留目标自带的 job/instance 标签
    sample_limit: 5000          # 单次抓取样本数上限（0 表示不限）
    body_size_limit: 10MB       # 响应体大小上限
    label_limit: 200            # 标签数量上限
    label_name_length_limit: 100
    label_value_length_limit: 500
    params:                     # 附加查询参数
      module: [http_2xx]
    authorization: { credentials_file: token.txt }
    tls_config: { ca_file: ca.cer, cert_file: client.cer, key_file: client.key }
    metric_relabel_configs: [...]   # 抓取后对样本做 relabel
    static_configs:
      - targets: ["localhost:9100"]
```

启动 flag（对应 `scrape.Options`）：

| flag | 作用 |
|------|------|
| `--scrape.adjust-timestamps` | 是否对抓取样本时间戳做对齐/容差处理（对应 `AlignScrapeTimestamps`） |
| `--scrape.timestamp-tolerance` | 时间戳对齐容差（默认 2ms，需为 2 的幂） |
| `--scrape.discovery-reload-interval` | 单目标配置变更的生效间隔（`DiscoveryReloadInterval`） |
| `--scrape.failure-log` | 抓取失败样本落盘文件（`ScrapeFailureLogFile`） |
| `--enable-feature=native-histograms` | 启用原生直方图抓取解析 |

### 2. 进程内代码入口（`cmd/prometheus/main.go`）

```go
// 1. 创建抓取管理器（main.go:788），写入目标为 fanoutStorage
scrapeManager, err := scrape.NewManager(
    &cfg.scrape,
    log.With(logger, "component", "scrape manager"),
    fanoutStorage,
    prometheus.DefaultRegisterer,
)

// 2. 配置热重载（main.go:950，reloader 名 "scrape"）
reloader: scrapeManager.ApplyConfig

// 3. 启动：消费服务发现的目标组（main.go:1143）
err := scrapeManager.Run(discoveryManagerScrape.SyncCh())
```

### 3. HTTP 接口入口（外部访问 Prometheus）

| 接口 | 说明 |
|------|------|
| `GET /api/v1/targets` | 抓取目标列表；`state=active`（默认）/`dropped`/`any`，含 `labels`、`discoveredLabels`、`scrapeUrl`、`health`、`lastError`、`lastScrape`、`lastScrapeDuration`、`scrapePool`、`globalUrl` |
| `GET /api/v1/targets/metadata` | 指定目标/指标的元数据（type/help/unit） |
| `GET /api/v1/metadata` | 全量指标元数据 |
| Web UI `/targets` | 目标列表页面（可查看 `discoveredLabels`、健康状态、最近错误） |
| Web UI `/config` | 展示当前 `scrape_configs`（脱敏） |

### 4. 出口（Prometheus → 被监控目标）

对每个目标发起 `GET {scheme}://{__address__}{metrics_path}?{params}`，发送 `Accept` 声明支持的格式
（Prometheus 文本 / OpenMetrics / Protobuf），并附带目标所需的认证与 TLS 配置。

### 5. CLI 入口（promtool）

```bash
promtool check config prometheus.yml           # 校验含 scrape_configs 的配置
promtool check service-discovery <job> --config.file=prometheus.yml   # 预演某 job 的 SD + relabel 结果
```

### 6. 可观测入口

| 入口 | 内容 |
|------|------|
| `GET /metrics` | 上述 `prometheus_target_*` 指标 |
| 时序数据 | 每个目标的 `up`、`scrape_duration_seconds`、`scrape_samples_scraped` 等 |
| Web UI `/targets` | 目标健康、最近抓取时间、错误信息 |

## 七、关键实现要点

| 关注点 | 说明 |
|--------|------|
| 每目标一 goroutine | 一个 `scrapeLoop` 独立调度，互不阻塞；配置变更时该目标的 loop 才重建 |
| 抓取错峰 | `Target.offset()` 用标签 hash 计算相位，使同 job 的目标均摊在 interval 内 |
| 目标去重与上限 | `scrapePool.sync` 对目标做格式化去重，受 `target_limit` 约束，超出计入指标 |
| relabel 两阶段 | `relabel_configs`（发现后、抓取前决定是否抓）+ `metric_relabel_configs`（抓取后、写库前决定是否保留样本） |
| honor_labels | 为 false 时目标自带的 `job`/`instance` 会被重命名为 `exported_job`/`exported_instance` |
| 限制保护 | body/sample/label/桶数量上限，超限则丢弃本次抓取（`up=0`）并计入对应指标 |
| staleness | 目标被移除或抓取失败时写入 stale marker，使查询不再返回旧值 |
| 时间戳对齐 | `--scrape.adjust-timestamps` 时把样本时间戳对齐到抓取时刻并加容差，避免远端的未来时间戳问题 |
| 元数据缓存 | 抓取时收集 `# HELP`/`# TYPE`/`# UNIT` 存入目标级 `MetricMetadataStore`，供 API 与 UI 展示 |
| 失败样本落盘 | `--scrape.failure-log` 把失败的抓取数据写入文件，便于离线排查 |
