# Prometheus notifier 目录结构说明

> 基于 Prometheus v2.53 源码整理。
> `notifier/` 是 Prometheus 的**告警通知（Notification）子系统**：接收规则引擎产生的告警，
> 经过去重/重标（relabel）/补齐 external labels 后，通过 HTTP 批量推送到
> 各 Alertmanager 实例（`POST /api/v2/alerts`）。
> 它随 `prometheus` 二进制运行（**Server 模式**；Agent 模式不启动），不是独立服务。

## 一、整体架构（告警流转链路）

```
 ① 产生告警
    rules.AlertingRule.Eval()            （rules/alerting.go）
        │  按 --rules.alert.resend-delay 判断是否需要发送（needsSending）
        ▼
    rules.SendAlerts(notifierManager, externalURL)  → NotifyFunc(ctx, exprStr, alerts...)
        ▼
 ② 入队
    Manager.Send(alerts...)
        │  • relabelAlerts：补 external labels（不覆盖已有）+ alert_relabel_configs
        │  • 队列超容量时丢弃最旧告警（dropped_total 计数）
        ▼
 ③ 发送循环
    Manager.Run(tsets <-chan map[string][]*targetgroup.Group)
        │  nextBatch()：每批最多 maxBatchSize=64 条
        │  sendAll()：并行向每个 alertmanagerSet 下的所有实例发送
        ▼
    sendOne() → HTTP POST {scheme}://{addr}{path_prefix}/api/{v1|v2}/alerts
        │  2xx 视为成功；至少一个 AM 成功则该批不算丢弃
        ▼
 ④ 地址发现（与抓取共用 SD 框架）
    discoveryManagerNotify.Run()  → SyncCh() → Manager.reload(tgs)
        → alertmanagerSet.sync() → AlertmanagerFromGroup()（含 relabel 过滤）

 ⑤ 观测：prometheus_notifications_* 指标 + GET /api/v1/alertmanagers
```

## 二、目录结构总览

```
notifier/
├── notifier.go        # ★ 全部实现：Alert 模型、Manager 队列与发送循环、
│                      #   Alertmanager 发现同步、HTTP 推送、通知指标
└── notifier_test.go   # 单元测试：队列容量/丢弃、relabel、API v1/v2 载荷、
                       #   AM 去重与 dropped 标记、SD 同步
```

> 本目录结构极简：**单文件实现**（`notifier.go`，约 770 行），无子目录。
> 相关的 Alertmanager 端点发现逻辑在 `discovery/`，告警产生在 `rules/`，
> Alertmanager 的 API 数据结构来自 `github.com/prometheus/alertmanager/api/v2/models`。

## 三、文件功能说明（`notifier.go`）

### 3.1 数据模型

| 元素 | 作用 |
|------|------|
| `Alert` | 生态通用的告警表示：`Labels`（最小需含 `alertname`，决定告警身份）、`Annotations`（不参与身份）、`StartsAt`/`EndsAt`（活动时间窗）、`GeneratorURL`（回链 Prometheus） |
| `Alert.Name()` | 返回 `alertname` 标签值 |
| `Alert.Hash()` | 告警标签集哈希，用于告警身份去重 |
| `Alert.Resolved()` / `ResolvedAt(ts)` | `EndsAt` 已过则视为已恢复 |
| `alertmanager` / `alertmanagerLabels` | Alertmanager 端点的抽象；从发现标签中取 `__scheme__`、`__address__`、`__alerts_path__` 构造 URL |
| `alertmanagerSet` | 一组共享同一份配置（`config.AlertmanagerConfig`）的 Alertmanager 实例集合，含 `ams`（有效）与 `droppedAms`（被 relabel 丢弃） |

### 3.2 Manager 与生命周期

| 元素 | 作用 |
|------|------|
| `Options` | 可配参数：`QueueCapacity`（队列容量）、`ExternalLabels`（全局 external labels）、`RelabelConfigs`（`alert_relabel_configs`）、`Do`（可替换的 HTTP 执行函数，便于测试）、`Registerer` |
| `NewManager(o, logger)` | 构造 Manager：初始化队列、`more` 通知 channel、上下文和指标 |
| `ApplyConfig(conf)` | **配置热重载入口**：更新 external labels 与 alert relabel 配置，并为每个 `alertmanager_config` 重建 `alertmanagerSet`（含 HTTP client / SigV4 / TLS） |
| `Run(tsets)` | **发送主循环**：优先处理 SD 目标更新，再从队列取批发送；队列非空则自我唤醒继续 |
| `Send(alerts...)` | 入队：先做 relabel + external labels，超容量丢弃最旧并计入 `dropped_total`，然后唤醒发送循环 |
| `Stop()` | 取消上下文，停止发送循环 |
| `Alertmanagers()` / `DroppedAlertmanagers()` | 返回当前有效/被丢弃的 AM URL 列表（供 API 展示） |

### 3.3 发送实现

| 元素 | 作用 |
|------|------|
| `maxBatchSize = 64` | 单批最大告警数，避免一次请求体过大 |
| `sendAll(alerts...)` | 遍历所有 `alertmanagerSet`，按 `api_version` 编码 JSON（v1 用 `Alert` 数组，v2 用 `models.PostableAlerts`），并行 `sendOne`；返回「是否至少一个 AM 成功」 |
| `alertsToOpenAPIAlerts()` / `labelsToOpenAPILabelSet()` | 转换为 Alertmanager v2 API 的 OpenAPI 模型 |
| `sendOne(ctx, client, url, body)` | 实际 HTTP POST：设置 `User-Agent: Prometheus/<version>`、`Content-Type: application/json`，非 2xx 视为错误 |
| `postPath(pre, version)` | 拼接推送路径 `/api/v1/alerts` 或 `/api/v2/alerts`（带 `path_prefix`） |
| `relabelAlerts()` | 先补 external labels（已存在则不覆盖），再应用 relabel 规则；`keep=false` 的告警被丢弃 |
| `newAlertmanagerSet()` | 由 `AlertmanagerConfig` 构建 HTTP client（TLS/认证），可选 SigV4 签名 |
| `alertmanagerSet.sync(tgs)` | 从发现的目标组中提取 AM 端点并**按 URL 去重**，同时初始化各 URL 的指标 label |
| `AlertmanagerFromGroup(tg, cfg)` | 把发现目标 + 目标组标签转成端点标签（含 scheme、path），应用 `relabel_configs`，校验 `__address__` 合法性；返回（有效, 被丢弃）两个列表 |

### 3.4 指标（`alertMetrics`）

| 指标 | 类型 | 含义 |
|------|------|------|
| `prometheus_notifications_latency_seconds` | Summary（按 alertmanager） | 发送延迟分位数（0.5/0.9/0.99） |
| `prometheus_notifications_errors_total` | Counter（按 alertmanager） | 发送失败次数 |
| `prometheus_notifications_sent_total` | Counter（按 alertmanager） | 成功发送的告警条数 |
| `prometheus_notifications_dropped_total` | Counter | 因发送失败或队列满而丢弃的告警数 |
| `prometheus_notifications_queue_length` | GaugeFunc | 当前队列长度 |
| `prometheus_notifications_queue_capacity` | Gauge | 队列容量（`--alertmanager.notification-queue-capacity`） |
| `prometheus_notifications_alertmanagers_discovered` | GaugeFunc | 当前发现且有效的 AM 数量 |

### 3.5 测试文件

`notifier_test.go` 覆盖：队列满时丢弃最旧告警、单批超过容量、`alert_relabel_configs` 过滤与 external labels 补齐、API v1/v2 载荷格式、Alertmanager 端点去重与 `droppedAms`、SD 目标组同步、发送失败计数等。

## 四、归属

- **归属服务**：Prometheus **Server 模式**的告警通知组件，随 `prometheus` 二进制运行；**不是独立服务、无自身监听端口**（它只是 HTTP **客户端**）。
  - 上游：`rules`（`SendAlerts` 注入 `NotifyFunc`）、`discovery`（`alertmanager_sd_configs` 发现 AM 端点）、`config`（`alerting` 段配置）、`model/relabel`；
  - 下游：各 Alertmanager 实例的 `/api/v1/alerts`、`/api/v2/alerts`；
  - Agent 模式**不启动** notifier（无规则引擎、无告警）。
- 该包也被外部项目作为库引用（如 Thanos Ruler 复用了类似实现思路）。

## 五、访问入口

### 1. 配置入口（`prometheus.yml`）

```yaml
alerting:
  alert_relabel_configs:              # 发送前对告警做 relabel（在 external labels 之后）
    - source_labels: [severity]
      regex: info
      action: drop
  alertmanagers:
    - api_version: v2                 # v1 | v2（默认 v2）
      timeout: 10s                    # 单次发送超时
      path_prefix: /alertmanager      # AM 的路径前缀（AM 用了 --web.route-prefix 时需要）
      scheme: http                    # 被 SD 目标标签覆盖
      static_configs:
        - targets: ["127.0.0.1:9093"]
```

启动 flag：

| flag | 作用 |
|------|------|
| `--alertmanager.notification-queue-capacity` | 告警队列容量（`Options.QueueCapacity`），满则丢弃最旧 |
| `--alertmanager.timeout` | 发送到 Alertmanager 的超时（已被 config 中 `timeout` 覆盖/替代） |
| `--rules.alert.resend-delay` | 同一告警重复发送的最小间隔（在 `rules` 侧生效） |
| `--web.external-url` | 用于生成告警的 `generatorURL` 回链 |

### 2. 进程内代码入口（`cmd/prometheus/main.go`）

```go
// 1. 创建（main.go:718）
notifierManager = notifier.NewManager(&cfg.notifier, log.With(logger, "component", "notifier"))

// 2. 注入给规则引擎作为告警出口（main.go:851）
NotifyFunc: rules.SendAlerts(notifierManager, cfg.web.ExternalURL.String()),

// 3. 提供给 Web 层，用于 /api/v1/alertmanagers 展示（main.go:879）
cfg.web.Notifier = notifierManager

// 4. 配置热重载（main.go:967，reloader 名为 "notifier"）
reloader: notifierManager.ApplyConfig

// 5. 启动/停止（main.go:1400 / 1405）
notifierManager.Run(discoveryManagerNotify.SyncCh())   // 消费 AM 服务发现结果
notifierManager.Stop()
```

### 3. HTTP 入口

**出口（Prometheus → Alertmanager）**：

| 目标地址 | 说明 |
|----------|------|
| `POST {scheme}://{addr}{path_prefix}/api/v1/alerts` | `api_version: v1` |
| `POST {scheme}://{addr}{path_prefix}/api/v2/alerts` | `api_version: v2`（默认） |

**展示入口（外部访问 Prometheus 自身）**：

| 入口 | 内容 |
|------|------|
| `GET /api/v1/alertmanagers` | `activeAlertmanagers` / `droppedAlertmanagers` URL 列表（`web/api/v1/api.go:378`） |
| `GET /api/v1/alerts` | 当前活跃告警（数据来自 `rules`，非本包） |
| Web UI `/alerts` | 告警列表页面 |
| `GET /metrics` | 上述 `prometheus_notifications_*` 指标 |

### 4. 可观测排查要点

| 现象 | 排查指标 |
|------|----------|
| 告警没到 AM | `prometheus_notifications_errors_total{alertmanager=...}` 增长、Prometheus 日志 `Error sending alert` |
| 告警被丢 | `prometheus_notifications_dropped_total` 增长（队列满或全部 AM 失败） |
| AM 地址不对 | `GET /api/v1/alertmanagers` 看 active / dropped（dropped 通常是被 `relabel_configs` 过滤或地址非法） |
| 发送慢 | `prometheus_notifications_latency_seconds` 分位数 |

## 六、关键实现要点

| 关注点 | 说明 |
|--------|------|
| 队列语义 | 容量满时**丢弃最旧的告警**（保留最新），并计入 `dropped_total`；单批最多 64 条 |
| 发送成功判定 | 一批告警只要**至少一个** Alertmanager 接收成功即视为未丢弃 |
| 重试策略 | 本包**不做重试**；依靠规则引擎按 `--rules.alert.resend-delay` 周期性重发 |
| 标签处理顺序 | 先补 external labels（不覆盖已有标签）→ 再应用全局 `alert_relabel_configs` → 最后应用每个 AM 配置的 `relabel_configs` |
| API 版本 | 支持 Alertmanager v1/v2 两种 JSON 载荷，v2 使用 Alertmanager 的 OpenAPI 模型 |
| 端点发现 | 复用 `discovery` 框架：`alertmanager_sd_configs`（static/consul/dns/k8s…），`__alerts_path__` 由 `api_version` + `path_prefix` 生成 |
| 认证 | 支持 `http_config`（TLS、basic auth、bearer、OAuth2）与 AWS SigV4 |
| 无持久化 | 告警队列在内存中，进程重启后丢失（活跃告警由 `rules` 从 `ALERTS_FOR_STATE` 恢复后重新发送） |
