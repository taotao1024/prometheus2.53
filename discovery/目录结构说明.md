# Prometheus 服务发现（discovery）目录结构说明

> 基于 Prometheus v2.53 源码整理。
> `discovery/` 是 Prometheus **服务端内置的服务发现（Service Discovery, SD）子系统**，
> 不是独立服务。它从各类来源（Kubernetes、Consul、DNS、云厂商等）发现抓取目标，
> 将目标组（`targetgroup.Group`）推送给抓取管理器（scrape manager）和通知管理器（notifier）。

## 一、目录结构总览

```
discovery/
├── README.md                        # SD 设计规范与新增 SD 开发指南
├── discovery.go                     # 核心接口定义（Discoverer / Config / Configs 等）
├── manager.go                       # SD 管理器核心（新实现，默认使用）
├── manager_test.go                  # Manager 单元测试
├── registry.go                      # Config 注册中心 + YAML 反射解析（*_sd_configs 键）
├── metrics.go                       # Manager 自身指标定义
├── metrics_refresh.go               # refresh 包指标定义
├── metrics_k8s_client.go            # Kubernetes client-go 全局指标
├── discoverer_metrics_noop.go       # 无指标 SD 的空实现
├── util.go                          # 指标注册/反注册工具
│
├── targetgroup/                     # 目标组数据结构（SD 与管理器间的数据契约）
├── refresh/                         # 通用"定时轮询"Discoverer 骨架
├── install/                         # 副作用导入：注册全部内置 SD
├── legacymanager/                   # 旧版 SD 管理器（平滑过渡用）
│
├── aws/ azure/ gce/ openstack/ ...  # 各云厂商 SD 实现
├── consul/ dns/ http/ file/ ...     # 各基础设施 SD 实现
├── kubernetes/                      # Kubernetes SD（最常用的 SD 实现）
└── xds/ zookeeper/ ...              # 其他协议类 SD 实现
```

## 二、核心文件功能说明

| 文件 | 功能 |
|------|------|
| `discovery.go` | 定义核心接口：<br>• `Discoverer`——所有 SD 机制必须实现的接口：`Run(ctx, up chan<- []*targetgroup.Group)`，通过 channel 向管理器推送目标组<br>• `Config`——SD 配置接口：`Name()` / `NewDiscoverer()` / `NewDiscovererMetrics()`<br>• `Configs`——`Config` 切片，自定义 YAML 序列化<br>• `DiscovererOptions` / `DiscovererMetrics` / `RefreshMetrics` 等辅助类型<br>同时内置实现 `static_configs`（`StaticConfig`，静态目标列表） |
| `manager.go` | SD 管理器核心：<br>• `Manager`——维护 provider 集合，聚合所有 SD 的目标并按 job 分组发送<br>• `ApplyConfig()`——配置热重载时增删 provider（已存在的保持不动）<br>• `Run()` / `SyncCh()`——后台发送协程 + 供消费者（scrape/notifier）读取的只读 channel<br>• `Provider` / `StaticProvider`——对单个 Discoverer 的封装（配置、取消函数、订阅者） |
| `registry.go` | 配置注册中心：<br>• `RegisterConfig()` 将 SD 注册为 `<name>_sd_configs` YAML 键（如 `kubernetes_sd_configs`）<br>• 通过 `reflect.StructOf` 动态生成结构体，实现配置的内联 YAML 解析/回写<br>• `RegisterSDMetrics()` 统一注册所有 SD 的指标 |
| `metrics.go` | Manager 自身指标：`prometheus_sd_failed_configs`、`prometheus_sd_discovered_targets`、`prometheus_sd_received_updates_total`、`prometheus_sd_updates_delayed_total`、`prometheus_sd_updates_total` |
| `metrics_refresh.go` | `refresh` 包的指标向量（`prometheus_sd_refresh_failures_total`、`prometheus_sd_refresh_duration_seconds`），定义在本包以避免 discovery↔refresh 循环依赖 |
| `metrics_k8s_client.go` | 注册 Kubernetes client-go 的全局指标（`prometheus_sd_kubernetes_http_request_*`、workqueue 指标等）。client-go 指标为进程级全局，因此在 main 中统一注册而非每个 K8s SD 实例各自注册 |
| `discoverer_metrics_noop.go` | `NoopDiscovererMetrics`：没有指标的 SD（如 static）使用的空实现 |
| `util.go` | `MetricRegisterer` 工具：批量注册/反注册指标，任一注册失败时回滚已注册部分 |
| `manager_test.go` | Manager 的单元测试 |
| `README.md` | SD 设计规范：什么样的机制适合做成 SD、元数据标签命名约定（`__meta_<sdname>_<key>`）、目标组 `Source` 唯一性要求、新增 SD 的 checklist |

## 三、基础设施子目录

| 子目录 | 功能 |
|--------|------|
| `targetgroup/` | 定义 `Group{Targets, Labels, Source}` 数据结构——SD 机制与管理器之间传递目标的标准数据契约。`Source` 用于唯一标识一个目标组（增删更新以此为准） |
| `refresh/` | 通用"定时轮询"型 Discoverer 骨架：各 SD 只需提供 `RefreshF` 拉取函数和刷新间隔，即可获得轮询、失败/耗时指标等通用能力（consul、dns、大部分云厂商 SD 都基于它） |
| `install/` | 仅有副作用：`_` 空导入所有内置 SD 包，触发其 `init()` 中的 `RegisterConfig()` 注册。Prometheus 二进制通过 `plugins/plugins.go` 完成等价注册 |
| `legacymanager/` | 旧版 SD 管理器实现，与 `manager.go` 的新实现并存，用于平滑过渡。通过 `--enable-feature=new-service-discovery-manager` 选择使用新实现（默认）或旧实现 |

## 四、各服务发现机制子目录

> 每个 SD 子目录的约定：实现 `discovery.Config` 接口（配置结构体 + `Name()` + `NewDiscoverer()`），
> 在包 `init()` 中调用 `discovery.RegisterConfig()` 完成注册；
> 元数据标签统一使用 `__meta_<sdname>_<key>` 前缀。

| 子目录 | SD 机制 | 配置键 | 说明 |
|--------|---------|--------|------|
| `aws/` | AWS EC2 / Lightsail | `ec2_sd_configs`、`lightsail_sd_configs` | 通过 AWS API 发现 EC2/Lightsail 实例 |

## 五、访问入口

### 1. 配置入口（prometheus.yml）

```yaml
scrape_configs:
  - job_name: xxx
    kubernetes_sd_configs:   # 由 registry.go 注册的 <name>_sd_configs 键
      - role: pod
    static_configs: [...]    # 内置实现（discovery.go 中 StaticConfig）
alerting:
  alertmanager_configs:
    - consul_sd_configs: []  # 告警管理器同样支持服务发现
```

### 2. 代码入口（cmd/prometheus/main.go）

```go
// 统一注册所有 SD 指标（进程生命周期内仅调用一次）
sdMetrics, err := discovery.CreateAndRegisterSDMetrics(prometheus.DefaultRegisterer)

// 创建两套管理器：抓取发现（scrape）与通知发现（notify）
discoveryManagerScrape = discovery.NewManager(ctxScrape, ..., sdMetrics, discovery.Name("scrape"))
discoveryManagerNotify = discovery.NewManager(ctxNotify, ..., sdMetrics, discovery.Name("notify"))

// 启动并将发现的目标组交给消费者
discoveryManagerScrape.Run()
scrapeManager.Run(discoveryManagerScrape.SyncCh())   // 抓取管理器消费
notifierManager.Run(discoveryManagerNotify.SyncCh()) // 通知管理器消费

// 配置热重载时刷新（main.go reloaders 中的 "scrape_sd" / "notify_sd"）
discoveryManagerScrape.ApplyConfig(c)
```

> Agent 模式下仅创建 scrape 一套发现管理器；通过 `--enable-feature=new-service-discovery-manager`
> 可在 `discovery.Manager`（新实现，默认）与 `legacymanager.Manager`（旧实现）间切换。

### 3. 对外可访问入口（HTTP）

服务发现本身不暴露 HTTP 服务，结果通过 Prometheus Web 服务查看：

| 入口 | 地址 | 内容 |
|------|------|------|
| Web UI | `http://<prometheus>:9090/service-discovery` | 各 SD 发现的目标及 discovered labels |
| Web UI | `http://<prometheus>:9090/targets` | 抓取目标列表 |
| API | `GET /api/v1/targets?state=active` | 返回 `discoveredLabels` / `labels` / `scrapeUrl` 等 |
| 指标 | `GET /metrics` | 所有 `prometheus_sd_*` 指标 |

（配置了 `--web.route-prefix` / `--web.external-url` 时路径需加对应前缀。）

## 六、新增一个 SD 机制的标准步骤

参考 `README.md`：

1. 在 `discovery/` 下新建包，实现 `discovery.Config` 接口（`Name()`、`NewDiscoverer()`、`NewDiscovererMetrics()`）；
2. 在包 `init()` 中调用 `discovery.RegisterConfig()`；
3. 若需要轮询，基于 `refresh` 包实现 `Discoverer`；
4. 元数据标签使用 `__meta_<sdname>_<key>` 前缀，目标组带唯一 `Source`；
5. 在 `discovery/install/install.go`（或 `plugins/plugins.go`，需 `make plugins`）中 `_` 导入注册；
6. 在 `docs/configuration/configuration.md` 的 `<scrape_config>` 和 `<alertmanager_config>` 中补充文档；
7. 在 `config/testdata/conf.good.yml` 及相关测试中补充配置样例。
